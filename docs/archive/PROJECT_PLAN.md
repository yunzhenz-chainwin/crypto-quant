## 0. 設計總原則

### 0.1 前台:漸進式揭露(Progressive Disclosure)
一套介面用「**全域檢視模式切換**」+「**每張卡片可展開進階**」同時滿足三種人:

| 使用者 | 預設看到 | 行為 |
|---|---|---|
| 新手 | 簡易模式:白話、紅綠燈、emoji、一句話建議 | 不展開也能用 |
| 中度 | 簡易模式 + 偶爾展開「進階」學習 | 想懂時點開 |
| 老手 | 一鍵切「專業模式」= 現在的密集數字介面 | 全部數字、表格、參數 |

- Header 放一顆切換鈕「🌱 簡易 / 📊 專業」,選擇存 `localStorage`,預設簡易。
- 簡易模式把專業數字(夏普、獲利因子、MACD 數值、相關性矩陣、參數掃描…)收進「進階」摺疊,改用白話替代。

### 0.2 後台:同專案、`/admin` 路由、簡單帳密
- 不另開專案。沿用 FastAPI + React,後台走 `/admin/*`,共用同一套資料層。
- 認證:環境變數 `ADMIN_USER` / `ADMIN_PASS` → `/api/admin/login` 簽發 HMAC token → 前端存 `localStorage` → 所有 `/api/admin/*` 需帶 `Authorization`。簡單但不是明碼塞網址。

## 1. 前台人性化規劃

### 1.1 名詞「白話翻譯」對照(全站共用詞庫)
這是人性化的核心:把老手指標翻成人話。建一份 `frontend/src/constants/glossary.js` 統一管理。

| 專業 | 簡易模式顯示 | ⓘ 一句話解釋 |
|---|---|---|
| 信心分數 0–100 | 🟢偏多 / 🟡觀望 / 🔴偏空 紅綠燈 | 綜合多項指標的總分,越高越偏多 |
| RSI | 溫度計:便宜 / 正常 / 偏貴 | 最近漲太多(貴)還是跌太多(便宜) |
| MACD | 動能:↗ 增強 / ↘ 減弱 | 上漲或下跌的力道變化 |
| MA 均線排列 | 趨勢:多頭 / 盤整 / 空頭 | 短中期平均成本誰在上面 |
| 布林通道位置 | 偏高 / 中間 / 偏低 | 價格在常態波動帶的哪裡 |
| 夏普比率 | 划算度(冒一分險賺多少) | 越高代表報酬相對風險越划算 |
| 最大回撤 | 最慘縮水:從高點最多跌 X% | 帳面最痛的一段 |
| 獲利因子 | 賺的是賠的幾倍 | >1 才整體賺錢 |
| 超額報酬 | 比「買了放著」多賺/少賺 | 策略到底值不值得 |
| 相關性 | 會不會一起漲跌 | 高=連動、低=分散風險 |
| 年化波動度 | 刺激程度(價格多會跳) | 越高越大起大落 |

## 2. 後台管理台規劃

### 2.1 資訊架構(`/admin`,登入後)
```
/admin
 ├─ 登入頁(帳密)
 ├─ 總覽 Dashboard   ← 監控
 ├─ 操作 Operations  ← 手動觸發
 ├─ 管理 Manage      ← 內容/參數
 └─ 分析 Analytics   ← 使用數據
```

### 2.2 頁面一:總覽 Dashboard(監控)
卡片 + 紅綠燈呈現:
- **系統健康**:後端在線、排程器狀態、最後一次每日 pipeline 時間與成功/失敗。
- **資料新鮮度**:每幣 clean CSV 最後日期;落後(>1 天)標紅。
- **news.db 統計**:總筆數、各分類筆數、各來源筆數、最近抓取時間、有資料的日期分布。
- **外部來源狀態**:Binance / alternative.me / 各 RSS 最近一次成功與否。

### 2.3 頁面二:操作 Operations(手動觸發)
- 按鈕:抓 K 線(全部/指定幣)、重算指標、重算相關性、重跑回測、抓最新新聞、回補歷史新聞(日期範圍)。
- 點擊 → 後端背景執行,回傳 job_id,前端輪詢進度/結果。
- 顯示「最近操作紀錄」(來自 `job_runs` 表)。

### 2.4 頁面三:管理 Manage(內容/參數)
- **幣種清單**:已集中到 `app_config.coins` 並可由後台增/刪/停用;新增幣會觸發抓資料。仍待補的是時線幣種/更多週期的後台 UI。
- **訊號因子權重**:目前寫死在 `_compute_score`。抽到設定 → 後台可調權重/門檻(進階)。
- **回測預設**:`-0.06 / 0.20` 等抽到設定。
- **新聞管理**:列表/搜尋/刪除不當或重複新聞、手動改分類或情緒。

### 2.5 頁面四:分析 Analytics(使用數據)
- 已有輕量 middleware 記錄 API 請求(路徑、幣種、時間、回應碼、耗時)存 `access_log`(僅路徑與幣種,不記個資)。
- 待呈現:每日造訪數、最熱門幣種、各 API 呼叫量、平均回應時間、錯誤率。

## 3. 後端與資料層(支撐前後台)

### 3.1 先修的「地基問題」(來自前兩回合稽核)
1. **統一訊號邏輯**:回測 `src/backtest.py` 用 3 因子數票,但前端建議用 6 因子計分 → 兩者不一致,回測無法佐證畫面建議。將回測改用同一套 6 因子計分。
2. **修新聞歷史**:`query_by_date` / 日期下拉改用 `published_at`(真實發布日)而非 `fetched_at`,加 `idx_published` 索引 → 讓 backfill 真的能依歷史日期查。
3. **設定集中化**:幣種清單與各預設值抽到 `app_config`(或 config.json),消除四處重複。

### 3.2 新增資料表(SQLite,可放 `data/app.db`)
```sql
-- 操作/排程紀錄(監控 + 操作頁共用)
job_runs(id, job_type, status, started_at, finished_at, message)

-- 使用分析
access_log(id, ts, path, symbol, status_code, latency_ms)

-- 設定(幣種、因子權重、回測預設)
app_config(key, value_json, updated_at)

-- 每日訊號快照(讓前台能畫「信心分數歷史」)
daily_signal(date, symbol, signal, score, close, rsi)

-- 恐懼貪婪歷史(自有,不必每次跟外部 API 還原)
fear_greed(date, value, label)
```
> (更新)依需求,市場 K 線/指標已一併入庫(`prices` / `indicators`);CSV 管線仍保留產出,DB 作為查閱與後續分析的中央儲存,未來抓到的數值也一併寫入。

### 3.3 新增 API(節錄)
```
POST /api/admin/login                 帳密 → token
GET  /api/admin/health                系統/排程/資料新鮮度
GET  /api/admin/db/stats              news.db + 各表統計
POST /api/admin/jobs/{type}           觸發操作(回 job_id)
GET  /api/admin/jobs                  操作紀錄 + 進度
GET/PUT /api/admin/config             讀/改設定(幣種、權重、預設)
GET/DELETE /api/admin/news            新聞列表 / 刪除
GET  /api/admin/analytics             使用數據
```

## 4. 分階段實作藍圖

| 階段 | 內容 | 產出 | 風險 |
|---|---|---|---|
| **P0 地基** | 統一訊號邏輯、修新聞歷史、設定集中化、建 SQLite 新表 | 系統自圓其說、可被監控 | 中(動到核心邏輯,需回測重驗) |
